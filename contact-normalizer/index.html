Contact Normalizer

Phones to E.164, e-mails validated, names and countries cleaned, offline, in bulk.

Open Contact Normalizer in the Apify Store

What it solves

Lead lists, CRM exports and form submissions arrive with phones as (650) 253-0000, +1 650-253-0000 and 6502530000, e-mails with stray spaces and capitals, and countries as USA, United States or us. Deduplicating or importing that data fails until it is in one shape.

Contact Normalizer cleans every record in one pass, offline: phones to E.164 with region and line type (Google's libphonenumber metadata), e-mails with RFC syntax validation and disposable, role-account and free-provider flags, names tidied, countries to ISO 3166-1 codes, with optional dedupe by e-mail and/or phone.

  • Each item has the untouched original, a drop-in normalized record (same keys, clean values), per-field details and an issues list with codes and plain-English fixes.
  • Records inline, from an Apify dataset (e.g. a lead-scraping run) or a CSV/JSON file URL; contact columns detected by name.
  • Optional Gmail canonical form (dots and +tags removed) and DNS MX check.
  • Deterministic: the same input always gives the same output.

Example output

One dataset item per input (abridged):

{
  "index": 0,
  "status": "ok",
  "valid": true,
  "normalized": {"name": "Ada Lovelace", "email": "ada.lovelace@example.com", "phone": "+16502530000", "country": "US"},
  "fields": {
    "phone": {"valid": true, "e164": "+16502530000", "national": "(650) 253-0000",
              "international": "+1 650-253-0000", "region": "US", "type": "fixed_line_or_mobile"},
    "email": {"valid": true, "domain": "example.com", "disposable": false, "role": false, "freeProvider": false}
  },
  "issues": [],
  "isDuplicate": false
}

// second record: "valid": false, with issues such as
{"field": "phone", "code": "PHONE_INVALID", "severity": "error",
 "message": "'+1 555 12' is not a valid number for country code +1 (wrong length or unassigned range). Check the digits and the country."}

Anything that can't be processed becomes an error item with a code and a message that says what to change; the rest of the run carries on.

Limits

  • Up to 1,000,000 records per run; dataUrl files up to 20 MB (use an Apify dataset for more).
  • Phone line type comes from numbering-plan metadata, not a live carrier lookup: no carrier name or reachability.
  • E-mail checks are syntax plus lists; checkMx confirms the domain accepts mail but never contacts a mailbox.
  • Names are tidied, not split or gender-guessed.

Privacy

Records are processed inside your run and stored only in its dataset and key-value store. No third party, no LLM. The optional MX check sends e-mail domains, never full addresses, to DNS resolvers. See also the privacy page.

FAQ

Does it verify that an e-mail address exists?

No. It validates syntax, flags disposable, role and free-provider addresses, and with checkMx confirms the domain has mail servers. It never probes mailboxes over SMTP.

How are numbers without a country code handled?

They are read in defaultCountry (US by default), or the record's own country column when useRecordCountry is on. Set defaultCountry empty to require a + prefix.

Can it tell mobile from landline?

For most countries, yes, from numbering-plan metadata. US and Canadian numbers can't be told apart offline and come back as fixed_line_or_mobile.

Can I clean the output of another Apify Actor?

Yes. Pick its dataset as datasetId; the Actor reads only the dataset you give it.

Is my contact data sent anywhere?

No. Processing happens inside your run. Only the optional MX check sends e-mail domains (never full addresses) to DNS resolvers.
